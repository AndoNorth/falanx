Falanx: pipeline topology + the output-contract mechanism

Two diagrams for the brainstorm. Diagram 1 is the whole system as it exists today (verified against workflow/runner.rs, orchestrator/, session.rs). Diagram 2 zooms into one agent invocation and shows the output-contract mechanism we designed — not yet built — replacing the current copy-pasted "respond with only JSON" prose in every prompt.md.

Diagram 1 — Current pipeline (whole system)

What happens between falanx run --diff and a finished session file, today.

Stage gating today

skip_if is a closed Rust enum (ScoreMeetsTarget, NoReviewIssues) — workflow/stage.rs. No custom predicates, no human checkpoint.

Loop exit, three conditions

Target score, max iterations (mandatory), plateau → horizon reset is a recovery attempt, not an exit — workflow/runner.rs::run.

What's missing here

falanx serve is a stub (main.rs:85) — CLI mode is the only path that actually runs today.

Diagram 2 — Inside one run_agent call: the output contract new / not built

One box from Diagram 1 ("score stage", "review stage", ...) actually runs one agent at a time through this. Everything inside the dashed boundary is the contract mechanism we just designed — it wraps whichever AgentKind executes, so it stays valid even if a future kind isn't a one-shot Cersei call.

What's genuinely new

  • output.schema.json per agent dir (optional)
  • agent/contract.rs: wrap + validate
  • AgentDef.output_schema, AgentRunResult.retry_diagnostics
  • SessionEvent::AgentOutputInvalid
  • jsonschema crate dependency

What stays unchanged

  • extract_output — still string-search JSON extraction
  • run_cersei — still one-shot, no tools/sandbox
  • synthesise_runs, TemplateContext shape
  • Cersei's own retry (transient provider errors only) — separate from this
